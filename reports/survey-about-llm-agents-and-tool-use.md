# LLM Agents and Tool Use: Architectures, Learning, and Evaluation

## TL;DR

- Tool-using agents range from prompted reasoning–action loops to models trained to make API calls and systems that execute code; these are different design choices, not directly comparable scores. ReAct interleaves reasoning and action, Toolformer trains API-call behavior, and CodeAct makes executable Python the action representation. [1] [2] [3]
- Agent improvement can target the agent program or model policy: AgentOptimizer edits external agent functions using task feedback, while ToolRL studies reinforcement-learning reward construction for tool selection and use. [4] [5]
- Evaluation must separate API competence, broader interactive capability, and safety. API-Bank and AgentBench have different scopes; ToolEmu and AgentDojo target different risk settings, so success on one is not a general reliability or security guarantee. [6] [7] [8] [9]
- Recent work makes learning and evaluation more systematic, but the evidence remains task- and setup-dependent; the evaluation survey argues for more holistic, realistic, scalable assessment. [5] [10]

## Background

An LLM agent can be understood here as a language model embedded in an interaction loop: it receives a task and observations, selects an action (which may invoke a tool), and uses the returned observation to continue. A tool call is therefore more than fluent text: it involves selecting an operation, supplying arguments, interpreting a result, and deciding whether another step is required. Benchmarks differ in which of these components they measure. API-Bank explicitly frames its runnable evaluation around planning, API retrieval, and API calling, while the evaluation survey distinguishes objectives such as capability, reliability, and safety from process choices such as interaction mode, benchmark, metric, and tooling. [6] [10]

The foundational architectural contrast is between inference-time orchestration and learned tool behavior. ReAct prompts a model to interleave verbal reasoning with task-specific actions, using external information or an environment as feedback. Toolformer instead generates and filters self-supervised API-call examples so the model learns when and how to call APIs within next-token prediction. Neither framing by itself establishes robust operation across arbitrary interfaces: ReAct results are tied to studied tasks and prompting, and Toolformer explicitly identifies limitations in tool chaining and interactive use in the paper's discussion. [1] [2]

## Architectures: from action traces to executable programs

ReAct treats agent behavior as a cycle of reasoning, action, and observation. Its conceptual advantage is legibility of the control loop: the model can state intermediate reasoning, act on the environment, then incorporate the result. The paper evaluates this approach across question answering/fact verification and embodied or web tasks, and reports task-specific gains, including absolute success-rate advantages on ALFWorld and WebShop. Those results support the value of the tested prompting paradigm, not universal superiority: the source notes particular model and task setups, and headline comparisons should not be transported to different environments without matched experiments. [1]

Toolformer shifts emphasis from composing a prompt-time loop to acquiring API-call behavior during training. It uses a handful of demonstrations per API and a self-supervised procedure to decide whether generated calls improve prediction. Its evaluations cover multiple tool categories, including question answering, search, calculation, translation, and calendar operations. The paper itself identifies important boundaries: Toolformer does not chain tools or interactively use them, is sensitive to wording, and does not account for API computational costs; these constraints limit what should be inferred from its tool-specific evaluations. [2]

CodeAct changes the action language: rather than restricting an agent to a fixed text/JSON schema, it uses executable Python integrated with an interpreter. The authors emphasize multi-turn execution and the ability to revise actions after observations, allowing composition of operations in code. Its abstract reports analysis of 17 LLMs on API-Bank and a newly curated benchmark, and up to 20% higher success rate against alternatives; this is a maximum reported result, not a uniform gain. The source does not establish execution safety, operational cost, or performance beyond the evaluated settings. Compared with ReAct and Toolformer, CodeAct broadens what an action can express, but it also makes an interpreter and controlled execution environment part of the system assumptions. [3]

| Design | What is changed | Evidence and scope | Principal caveat |
|---|---|---|---|
| ReAct | Prompted reasoning/action/observation cycle | Evaluated on language and interactive tasks; task-specific success improvements reported | Depends on prompt, model, and environment; not a generic guarantee [1] |
| Toolformer | Training data and model behavior for API insertion | Self-supervised API learning across several tool categories | No chaining or interactive tool use in the described method [2] |
| CodeAct | Executable Python as action space | 17-model analysis; maximum reported success-rate improvement | Execution safety and broad deployment behavior are not established [3] |

## Learning to improve tool behavior

Learning approaches intervene at different system layers. AgentOptimizer treats the agent's functions as learnable parameters while leaving base model weights unchanged. It uses an LLM to propose incremental add, revise, or remove operations informed by execution histories and task performance; its described safeguards include withdrawing updates after degraded training-set performance and stopping after consecutive non-improving steps. This is an offline program-improvement paradigm rather than gradient-based optimization of the LLM. The retrieved evidence reports improvements on downstream tasks but does not provide enough benchmark-specific values to establish effect size, out-of-distribution transfer, or freedom from training-set overfit. [4]

ToolRL instead studies reinforcement-learning rewards for tool selection and application. Its primary abstract reports a structured reward design and training with GRPO, and reports gains of 17% over base models and 15% over supervised fine-tuned models across diverse benchmarks. The follow-up full-text evidence includes an API-Bank result for a particular Qwen2.5 1.5B setup (44.0% for the reported GRPO cold-start condition versus 20.8% raw and 24.8% SFT400); those figures are benchmark- and model-specific and should not be mistaken for a general effect. The paper's analysis cautions that longer reasoning traces are not inherently better and discusses reward scale, granularity, and dynamics, highlighting the challenge of rewarding valid tool selection and arguments rather than only final answers. [5]

Search-R1 illustrates a narrower environment-learning pattern: reinforcement learning trains multi-turn reasoning and search interactions, with retrieved passage tokens excluded from the policy loss and generated reasoning/tool-call tokens optimized. It reports gains against RAG baselines on seven QA datasets for the specified model sizes. The authors identify combining search with a more diverse tool set as future work, so it is evidence about search-centered agent training rather than general function calling. Tool-R1 is a further recent direction described as sample-efficient RL for multi-step tool use via executable Python, and the available summary reports about a 10% gain on GAIA; it does not provide an exact sample-efficiency measure or detailed comparative results, so stronger comparisons would exceed the evidence. [11] [12]

Together, these methods reveal a design choice between improving a controller outside the model and optimizing the model's policy with reward. The evidence does not provide a controlled head-to-head comparison of AgentOptimizer and ToolRL. Their objectives, training interfaces, and evaluations differ, so it is reasonable to view them as complementary options rather than rank them from the reported results. [4] [5]

## Evaluation: capability is not reliability or safety

API-Bank is focused on tool-use operations. Its benchmark evaluation system comprises 73 API tools and 314 annotated dialogues containing 753 API calls, designed to assess planning, retrieval, and calling. These scopes should not be conflated with its broader training collection of APIs and dialogues. API-Bank offers a concrete basis for testing API-level competence, but a curated runnable benchmark does not by itself show performance against changing live APIs or establish safe use. [6]

AgentBench asks a broader question: how well do LLMs act across interactive environments? It contains eight distinct environments, and the cited HF record reports an evaluation of 25 API-based and open-source models. Its analysis identifies long-term reasoning, decision-making, and instruction following as obstacles. This breadth complements API-Bank, but makes its aggregate notion of agent capability different from a direct API parameter-accuracy test. The results are tied to the benchmark and model versions studied, not current universal rankings. [7]

Safety benchmarks ask questions capability suites may not answer. ToolEmu uses an LM to emulate tool execution and an LM-based evaluator to identify risks; its initial benchmark contains 36 high-stakes toolkits and 144 test cases, centered on underspecified instructions. The cited registry date is the HF discovery record date (2023-09-25), not the arXiv page's later displayed publication/update metadata. The authors report that the safest tested agent still exhibited evaluator-identified failures in 23.9% of cases and that 68.8% of failures identified by ToolEmu were validated as realistic by human evaluation. These are meaningful checks of the proposed emulation framework, but LM-emulated tools and evaluation are not equivalent to independently verifying every real-world consequence. The paper also notes that case curation remains substantially human-dependent. [8]

AgentDojo targets prompt injection in agents that use tools over untrusted data. It is a dynamic, extensible environment with 97 tasks and 629 security test cases. The paper reports that evaluated state-of-the-art systems fail many benign tasks even without attacks and that attacks break some, but not all, tested security properties. This complements ToolEmu's underspecification-oriented risk tests: the threat models differ, and neither benchmark exhausts the full space of safety failures. Scores should therefore be interpreted as evidence under the benchmark's tasks, attacker strategies, and agent configurations. [9]

The evaluation survey supplies a useful synthesis rather than a new empirical ranking. It organizes evaluation by objectives—behavior, capability, reliability, safety—and by process, including interaction, benchmarks, metric computation, and tools. It also flags enterprise issues such as role-based access, reliability guarantees, dynamic long-horizon interactions, and compliance. This taxonomy explains why no single benchmark score suffices: API correctness, long-horizon task completion, and resistance to malicious or untrusted content are distinct claims requiring different evidence. [10]

## Trends and open problems

Across architectures, training, and evaluation, the field is moving from simple call generation toward multi-step interaction, compositional actions, learned adaptation, and risk-aware testing. Code execution can make actions more composable; RL reward studies distinguish formatting and tool-call correctness; dynamic benchmarks test untrusted information. These advances are not directly comparable and their reported benefits remain bounded by the relevant benchmark and setup. [3] [5] [9]

Several open problems follow from the evidence. First, interoperability and robustness: methods must handle changing tool schemas, failures, ambiguous arguments, and multi-step dependencies, while Toolformer explicitly lacks chaining and ToolRL's generalization evidence is limited to studied settings. Second, safe execution and data handling: the CodeAct source does not establish security of generated code, while AgentDojo demonstrates why tools operating over untrusted data require separate attack testing. Third, evaluation realism and reproducibility: API-Bank is curated, AgentBench aggregates distinct interactive environments, and ToolEmu relies on emulation; stronger conclusions need transparent protocols and complementary live or independently verified tests. [2] [3] [5] [6] [7] [8] [9]

Finally, efficient improvement remains unsettled. AgentOptimizer's external-function edits and ToolRL's policy optimization address different bottlenecks, but the sources do not establish which is more sample-efficient or robust under distribution shift in a shared test. A useful next step is matched evaluation that reports task success, call correctness, interaction cost, recovery from tool errors, and safety outcomes separately. The evaluation survey's call for holistic, realistic, scalable assessment supports this direction; it remains a synthesis of prior work rather than empirical validation of a particular protocol. [4] [5] [10]
